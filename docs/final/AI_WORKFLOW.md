# Virtual Coach · AI 协作开发记录

> 目的：记录用 AI 编程 Agent 把 Virtual Coach 从想法做到可运行原型与文档的关键提示词与协作过程。
> 日期：2026-06-23

---

## 0. 协作中的提示词原则

贯穿全程的几条习惯：

1. **先让 AI 读懂现状再动手**——任何改动前先"读代码/读文档，复述你的理解"。
2. **一次只收敛一个决策**——大需求拆成"先对齐设计 → 再写计划 → 再逐步实现"，不一口气下发。
3. **给硬约束**——技术栈、不要做什么、视觉风格（如"禁用阴影、扁平描边"）、"不许编造坐标/数据"都写进提示词。
4. **要求自验证**——每步都让 AI 跑 `npm test` / `tsc` / `build` 并回报结果，再继续。
5. **设计与实现保持一致**——改了功能就同步更新文档，避免文档与产品脱节。

## 2. 想法 → 重新设计

### 提示词
```text
我要重新设计这个项目的架构和功能。功能上回放和复盘保留，先去掉生成 HTML 预览。
我想要的首页：进浏览器就是满屏地图，下方一个像 Claude/GPT 那样的对话框，带一个“＋”可以
上传 fit/gpx。可以和 AI 自然语言聊天，但范围我来限制。首页要简洁高级。
核心功能：用户在对话框让 AI 教练生成任意公里数的跑步路线，起点可以是当前位置，也可以

```

### AI 处理
没有直接写代码，而是先进入需求澄清：逐个确认"路线是否要贴真实道路""聊天范围边界""起点选择方式"等，并指出**纯 LLM 直接吐坐标不可行**、真实路网需要路由引擎。

### 产出
确定方向：贴真实路网、地图满屏 + 对话叠加层、AI 严格限定跑步范围。

## 3. 关键技术决策

### 提示词
```text
路线一定要贴真实道路/步道，保持纯前端。
MapTiler 这个 key 能做路由吗？
```

### AI 处理
联网核实后给出结论：**MapTiler 路由仍是 beta、不可用**；改用 **OpenRouteService**——原生支持"环线生成（round trip）"，给起点 + 目标距离 + 随机种子即可沿真实步道生成回到起点的闭环，且有 `foot-walking` / `foot-hiking` 两种步行 profile，免费额度足够。

### 产出
技术底座：MapTiler（底图/地名/高程）+ ORS（路由/环线）+ Kimi/DeepSeek/OpenAI/Google Gemini/Qwen（对话 + 工具调用）。

## 4. 设计 → 计划 → 逐步实现

### 提示词
```text
按我们确认的设计，先写一份设计文档；我确认后再拆成一份逐任务的实现计划，
每个任务都先写测试再写实现（TDD），并且每步跑测试/构建验证。
```

### AI 处理
1. 产出设计文档（架构、模块拆分、Agent 工具集、环线"凑距离"算法、错误处理、测试策略）。
2. 拆成多个小任务，每个含"失败测试 → 最小实现 → 跑通 → 提交"。
3. 逐任务实现：路由（`ors.ts` 距离 ±5%/3 轮逼近）、地名、GPX 导出、训练摘要、LLM provider（含 key 测试）、Agent 工具与对话循环、地图与图层、对话框、设置齿轮，最后重写 `App.tsx` 外壳。
4. 每个模块单测 + `tsc` / `build` 门禁。

### 产出
可运行原型成型：满屏地图 + 对话框，能生成真实环线/点到点、下载 GPX、上传 FIT 回放 + AI 复盘；`App.tsx` 从 1182 行拆成约 300 行的状态编排外壳。

## 6. 迭代二 · 路线体验升级

### 提示词
```text
1）生成的 GPX 没有海拔，路线明明覆盖山路却没有爬升数据。
2）用户怎么手动选起点？AI 该在对话里弹个卡片问“用当前位置还是手动选点”，
选手动后鼠标变大头针，点地图弹确认，确定后再生成路线。
3）如果能分越野跑和路跑，就该问用户要哪种，再去选合适的山路或道路。
```

### AI 处理
同样先对齐设计再实现：
- **海拔**：解析时保留每点高程，GPX 写入 `<ele>`；
- **越野/路跑**：`foot-hiking` / `foot-walking` 双 profile，AI 按地形选；
- **引导卡片**：撤掉旧的三段切换器，改为 AI 缺地形/起点时弹卡片（`ask_run_terrain` / `ask_start_point`），手动选点 = 十字光标点图 + 确认；信息齐全则零卡片直接生成；任意卡片可取消。
逐任务 TDD 实现，整体复审后修掉"选点未落针时无 UI / 无退出"的问题。

### 产出
路线更真实可用（带爬升）、能分路面、起点交互引导清晰自然。

## 9. 迭代三 · FIT 导入后的回放优先

### 提示词
```text
这是我导入一个人的fit后，你看看左边聊天框里的排版，你感觉拥挤不，是不是优化一下呢？
还有，地图下方的没有播放按键啊。
另外有一个问题，就是我上车fit后，聊天框直接就开始复盘了，这个是不是应该我手动的在聊天框确认呢？
如果我只是想播放跑步回放，我直接上传完按下面的播放就好了
```

### AI 处理
- 先看截图和代码，定位到上传后 `App.tsx` 直接 `send("[上传训练] ... 请复盘")`，这是自动复盘的来源；
- 改成上传后只解析文件、绘制轨迹、显示回放条，并在聊天栏放一个“训练已导入”确认卡；
- 确认卡展示文件名、距离、时长，提供“开始复盘”按钮，用户点击后才带 `run_id` 调 AI；
- 给 `ReplayBar` 增加播放/暂停按钮，播放时移动地图 runner marker；
- 放宽左侧聊天栏宽度与消息间距，补齐 Markdown 表格样式，避免复盘报告在窄气泡里过度拥挤。

### 产出
跑后体验从“上传即被长复盘打断”改为“先看轨迹回放，想复盘再确认”；聊天栏更像工具面板，不再把完整报告硬塞进第一屏。

## 10. 迭代四 · 海拔坡度图与回放倍速

### 提示词
```text
播放的时候能不能下方或者背景配上海拔图呢，我好知道什么时候是上坡或者平路或者下坡，
而且播放的时候是不是可以选择倍速，有真实速度，最高8倍速
```

### AI 处理
- 将回放推进从“固定平均速度扫完整条路线”改为按 FIT 原始时间戳推进，再映射到当时的距离位置；
- 增加倍速选择：真速(1x)、2x、4x、8x，最高限制为 8x，默认 8x 便于快速看完整段；
- 在底部回放条中加入海拔坡度图，按距离采样海拔：橙色表示上坡，蓝色表示平路，绿色表示下坡；
- 播放/拖动时显示同步竖线和当前点，并给出“上坡/平路/下坡”与当前海拔；
- 增加移动端样式压缩规则，避免底部回放工具遮挡左侧聊天框。

### 产出
回放从“轨迹点移动”升级为“可解释地形回放”：用户能把配速/心率变化和坡度变化对应起来，快速判断哪里是上坡、平路或下坡。

## 11. AI 应用与价值复盘

**产品里的 AI**
- LLM 负责理解自然语言、按需弹卡片收集地形/起点、生成训练建议；
- 路线坐标由真实路网 API 返回、训练分析先本地抽结构化摘要再交 AI 解释——**从结构上抑制幻觉**；
- Agent 有明确工具边界与"只谈跑步"的领域限制；
- FIT 上传后先由本地回放界面承担“看数据”的任务，AI 只在用户确认后进入复盘，减少不必要调用，也让用户保留节奏控制权。

**开发过程里的 AI**
- 读代码定位现状 → 需求澄清 → 写设计/PRD → 拆任务 → TDD 逐步实现 → 自动跑测试/构建/复审 → 看真机截图迭代 → 出文档；
- 全程"文档先行、改动即同步文档"，避免实现与文档脱节。

**带来的效率**
- 在同一会话内完成：架构重构（`App.tsx` 1182 → 约 300 行）、7 个 Agent 工具、63 项测试、多轮功能迭代、一键启动应用与全部文档；
- 把"查地图试距离导格式""手动读配速心率"这类重复工作，压缩成一次对话与一次上传。
